# Infra Agent — Stratum Context

## Role

You own the infrastructure layer: `docker-compose*.yml`, `install.sh`, `bootstrap.sh`, `Makefile`, `.env.example`, and `hasura/apply-migrations.sh`. You do NOT touch `nestjs/src/` or `hasura/metadata/` unless it's a permissions/path fix.

## Project Structure

```
stratum/
├── docker-compose.base.yml     # Core stack template (Postgres + Hasura + NestJS)
├── docker-compose.storage.yml  # Storage module overlay (RustFS + WebUI)
├── docker-compose.yml          # Generated by install.sh — NOT committed
├── install.sh                  # Interactive setup: generates .env + docker-compose.yml
├── bootstrap.sh                # One-shot bootstrapper: downloads template + runs install logic
├── .env.example                # Canonical env template — committed
├── .env                        # Generated by install.sh — NOT committed
├── Makefile                    # Developer + agent interface
└── hasura/
    └── apply-migrations.sh     # Runs inside Docker: applies metadata then migrations
```

## Key Rules

### install.sh safety

- Always guard with: `[[ -f ".env.example" && -d "hasura" && -f "docker-compose.base.yml" ]]`
- Use explicit `if [[ -f "$file" ]]; then sed ...; fi` — never `cmd && other || true` (swallows errors)
- Secrets must be generated via `/dev/urandom` — never hardcoded
- Clean up `.bak` files after `sed -i.bak`

### docker-compose conventions

- NestJS port 3000 is **NOT exposed** to host — internal only, Hasura calls it via Docker network
- Hasura port 8080 is the sole public interface
- All services use `${PROJECT_NAME:-stratum}` prefix for container names
- `hasura-apply-migrations` is `restart: "no"` — runs once and exits

### Optional modules (Storage)

Storage is toggled by `STORAGE_ENABLED` in `.env`. The pattern:

- **In metadata**: wrap optional sections with `# STORAGE_START` / `# STORAGE_END` markers
- **In install.sh**: `sed '/# STORAGE_START/,/# STORAGE_END/d'` strips sections for core-only
- **Template overlay**: `.template/storage/` contains files that are overlaid when storage is enabled

### apply-migrations.sh order

MUST apply in this order:
1. `hasura-cli metadata apply` first
2. `hasura-cli migrate apply` second

Reversing the order breaks migrations (database sources must exist before running schema changes).

### Makefile targets

Every new lifecycle operation must have a `make` target. Current targets:

| Target | Purpose |
|---|---|
| `make up` | `docker compose up -d` |
| `make down` | `docker compose down` |
| `make reset` | down -v + up (clean slate) |
| `make logs` | tail all service logs |
| `make ps` | container status |
| `make test` | run all tests |
| `make test-smoke` | verify running stack health |
| `make test-install` | verify install script output |

## Environment Variables

When adding a new env var:
1. Add to `.env.example` with a safe default or clear placeholder
2. Add to the relevant `environment:` section in `docker-compose.base.yml`
3. If required (no default), use `:?VAR is required` syntax in docker-compose
4. Document in README if user-facing

## Verification

After any infra change:

```bash
make test-install   # verify install.sh output (no Docker needed)
make reset          # clean restart
make test-smoke     # verify all services healthy
```

Check migration logs specifically:
```bash
docker logs stratum_hasura_apply_migrations
```

## What NOT to Touch

- `nestjs/src/` — NestJS source is owned by the NestJS agent
- `hasura/metadata/` YAML files — owned by the Hasura agent (except permissions/path fixes)
- `hasura/migrations/` SQL files — owned by the Hasura agent
